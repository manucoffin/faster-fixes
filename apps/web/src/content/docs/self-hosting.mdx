---
title: Self-hosting
description: Deploy FasterFixes on your own infrastructure. Host the dashboard, the widget API, and the MCP server without relying on the cloud version.
---

FasterFixes is AGPL-3.0. You can deploy the full stack on your own infrastructure: dashboard, widget API, and background jobs. This guide covers the minimal setup for a production deployment.

The widget packages (`@fasterfixes/widget`, `@fasterfixes/react`, `@fasterfixes/core`) are MIT-licensed and can be embedded in any client project regardless of where you host the backend.

## Requirements

You will need:

- A **Node.js host**: Vercel is recommended (the repo is a Next.js app), but anything that runs Next.js will work (Railway, Fly, self-managed).
- A **PostgreSQL database**: Neon, Supabase, Railway, or self-managed.
- An **Inngest** account for background jobs (screenshot processing, GitHub sync, etc.). The free tier is enough to get started.
- A **storage backend** for screenshots and images: Cloudflare R2 (the default), AWS S3, an S3-compatible server such as MinIO, or persistent local disk.
- An **SMTP server**, **Resend**, or **Plunk** for transactional email: required to send sign-up confirmations and password resets.
- (Optional) A **GitHub App** if you want the GitHub integration.

Stripe is not needed for self-hosted installs. The billing code only runs on the hosted cloud version.

## 1. Clone and deploy

Fork or clone [the repository](https://github.com/manucoffin/faster-fixes), then deploy the `apps/web` workspace to your host.

```bash
git clone https://github.com/manucoffin/faster-fixes.git
cd faster-fixes
pnpm install
```

On Vercel, import the repo and set the root directory to `apps/web`. Vercel auto-detects Next.js and Turborepo.

## 2. Configure environment variables

Copy `apps/web/.env.example` and fill in the values. The minimum set for a self-hosted deployment:

```bash
# Core
DOMAIN_NAME="your-domain.com"
BASE_URL="https://your-domain.com"
DATABASE_URL="postgresql://user:password@host:5432/db?schema=public"

# Auth
BETTER_AUTH_SECRET="<generate with: openssl rand -base64 32>"
BETTER_AUTH_URL="https://your-domain.com"

# Storage (Cloudflare R2, default). The bucket can stay private.
STORAGE_REGION="auto"
STORAGE_BUCKET_NAME="your-bucket"
R2_ACCOUNT_ID="..."
R2_ACCESS_KEY_ID="..."
R2_SECRET_ACCESS_KEY="..."

# Inngest (required in production)
INNGEST_EVENT_KEY="..."
INNGEST_SIGNING_KEY="..."

# Transactional email: required for sign-up confirmations and password resets.
# Resend remains the default. Set "plunk" or "smtp" to select another provider.
MAILER_PROVIDER="resend"
RESEND_API_KEY="re_..."
# PLUNK_SECRET_KEY="sk_..."
# For your own SMTP server, use the SMTP configuration below instead.

# Widget API (points clients' widgets at your instance)
NEXT_PUBLIC_FF_API_ORIGIN="https://your-domain.com"

# Self-hosted flag (keep false to skip marketing pages)
NEXT_PUBLIC_IS_CLOUD="false"
```

GitHub App variables are optional. Skip them unless you need the GitHub integration. Leave the Stripe variables unset. Billing is cloud-only and self-hosted installs don't run it.

For local disk, replace the storage variables above with `STORAGE_PROVIDER=local`. See the storage options below for optional overrides.

## 3. Provision external services

### PostgreSQL

Any Postgres 14+ works. Create a database and put the connection string in `DATABASE_URL`.

The adapter is selected from the `DATABASE_URL` hostname in every environment: hosts ending in `.neon.tech` use Neon's serverless adapter; other hosts use standard TCP PostgreSQL. `NODE_ENV` does not select the adapter. Set `DATABASE_PROVIDER=postgres` or `DATABASE_PROVIDER=neon` to override detection, including when using a custom hostname or proxy.

### Storage

Existing R2 variables work unchanged, with no provider toggle required. Create a bucket and a scoped API token. For AWS S3, use `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_BUCKET_NAME`, and optionally `AWS_REGION` instead. For an S3-compatible service such as MinIO or SeaweedFS, also set `STORAGE_ENDPOINT`; custom endpoints use path-style addressing unless `STORAGE_FORCE_PATH_STYLE=false`. `STORAGE_PROVIDER`, `STORAGE_BUCKET_NAME`, and `STORAGE_REGION` are optional overrides.

The bucket does not need to be public. Organization logos and user avatars are requested from `/api/storage/<bucket>/<key>` on your instance, which redirects to a short-lived signed URL for the object. Browsers must be able to reach the storage endpoint, which is already the case since uploads go to it directly. If you serve the bucket through a public URL or a CDN, set `NEXT_PUBLIC_STORAGE_BASE_URL` to that URL and logos and avatars are loaded from it instead. The bucket name is read at build time, so set the storage variables before building.

#### Bucket CORS for video uploads

Videos are uploaded from the browser straight to the bucket in 16 MiB parts, and the browser reads the `ETag` response header after each part to complete the upload. The bucket therefore needs a CORS rule that allows `GET`, `HEAD`, `PUT`, `POST` and `DELETE` from your app origin and exposes `ETag`. The same rule lets the review page capture video frames.

```json
[
  {
    "AllowedOrigins": ["https://feedback.example.com"],
    "AllowedMethods": ["GET", "HEAD", "PUT", "POST", "DELETE"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

- **Cloudflare R2**: paste the rule above into the bucket's CORS policy in the dashboard.
- **AWS S3**: wrap the array in `{ "CORSRules": [...] }` and apply it with `aws s3api put-bucket-cors --bucket your-bucket --cors-configuration file://cors.json`.
- **MinIO**: CORS is set server-wide. Allow your app origin with `mc admin config set <alias> api cors_allow_origin="https://feedback.example.com"`, then restart the server. MinIO exposes `ETag` to the browser by default.

#### Abandoned video uploads

A closed tab leaves an incomplete multipart upload behind. Faster Fixes removes the reserved Video after a day, but the parts already sent are cleaned up by the storage provider. R2 aborts incomplete multipart uploads after 7 days by default. S3 keeps them until a lifecycle rule aborts them, so add one:

```json
{
  "Rules": [
    {
      "ID": "abort-incomplete-video-uploads",
      "Status": "Enabled",
      "Filter": { "Prefix": "videos/" },
      "AbortIncompleteMultipartUpload": { "DaysAfterInitiation": 7 }
    }
  ]
}
```

Apply it with `aws s3api put-bucket-lifecycle-configuration --bucket your-bucket --lifecycle-configuration file://lifecycle.json`.

For local disk, set only `STORAGE_PROVIDER=local`; no storage credentials are needed. Files default to `./storage` in the application directory and the bucket to `uploads`, so images are served from `/api/storage/uploads`. Override these with `STORAGE_LOCAL_PATH` or `STORAGE_BUCKET_NAME` if needed. Use a persistent, application-managed directory shared by all app replicas, and back it up alongside PostgreSQL. Local URLs use the existing `BETTER_AUTH_SECRET` and app URL configuration.

#### Videos on local disk

With local disk, a video is uploaded in a single request that your instance streams to disk, so the largest video you can upload is bounded by your reverse proxy's request body limit. nginx defaults `client_max_body_size` to `1m`; raise it to at least the largest file you expect, for example `client_max_body_size 4g;` in the server block for your instance. Playback needs no extra configuration: `/api/storage` answers HTTP Range requests for videos, so the player can seek.

Screenshots stay private with every provider: they are only ever reached through signed URLs, and `/api/storage` serves nothing but logo and avatar keys without a token. To switch storage backends, copy existing files to the new bucket or directory with their keys unchanged, then update the storage configuration and rebuild. Asset rows do not need updating: reads and deletes always use the current provider and bucket. Previously issued signed URLs must be regenerated.

### Inngest

Create an app at [inngest.com](https://www.inngest.com). Copy the event key and signing key. After your first deployment, connect Inngest to your instance at `https://your-domain.com/api/inngest`.

### SMTP

Set `MAILER_PROVIDER=smtp` to use your own mail server instead of Resend or Plunk:

```bash
MAILER_PROVIDER=smtp
SMTP_HOST=mail.example.com
SMTP_PORT=587
SMTP_SECURE=false
SMTP_REQUIRE_TLS=true
SMTP_USER=your-smtp-username
SMTP_PASSWORD="your-smtp-password"
EMAIL_FROM="FasterFixes <support@example.com>"
```

Port 587 uses STARTTLS. For implicit TLS on port 465, set `SMTP_PORT=465` and `SMTP_SECURE=true`. Set both `SMTP_USER` and `SMTP_PASSWORD`, or leave both unset for an unauthenticated relay. Only disable `SMTP_REQUIRE_TLS` for a trusted local server that does not support TLS.

Use a sender address authorized by your mail server. `EMAIL_FROM` overrides both transactional sender addresses. Alternatively, `MAIL_FROM_DOMAIN` sets the domain for `contact@` and `noreply@` addresses without changing the application domain.

SMTP does not need Resend or Plunk API keys. It sends rendered transactional emails, but has no contact-management API, so marketing contact/segment synchronization is skipped. Keep credentials in your private environment file, not in Git.

## 4. Run migrations

From the repo root, with `DATABASE_URL` set to your production database:

```bash
pnpm --filter @workspace/db migrate:prod
```

This applies all pending Prisma migrations. Run it on every deploy. Do not use `migrate:dev` in production.

## 5. Verify

After the first deploy:

1. Visit `https://your-domain.com/login` and create the first account (becomes the admin).
2. Create a project, copy the widget API key, and test the widget in any page.
3. Check Inngest's dashboard to confirm events are being received.

Your instance is now ready. Point your clients' widgets at `NEXT_PUBLIC_FF_API_ORIGIN` and connect your AI coding agent via the [MCP server](/docs/mcp/setup).
