---
title: How It Works
description: Architecture overview of the feedback capture and delivery pipeline.
---

Faster Fixes has three main components: the widget, the API, and the consumption layer (dashboard + MCP).

## 1. Widget (client-side)

The widget runs in the reviewer's browser. In feedback mode, a hint next to the cursor names the two ways to make a Selection: click an element, or drag a rectangle over an area of the page. A drag selects an area that is not a single element, such as a gap between elements, part of a large image or chart, or whitespace. A tiny movement during a click still counts as a click, and touch screens keep tapping to select an element.

When they make a Selection:

- A screenshot of the viewport is captured (excluding widget UI)
- A smart DOM selector is generated with fallback strategies. For an area, it targets the area's container: the smallest element that holds the whole rectangle.
- On React sites, the React component tree is extracted (dev builds)
- Browser metadata is collected (name, version, OS, viewport)
- Where the Selection sat on screen is recorded: the element and the click point, or the rectangle of the area
- Recent console logs and network requests are captured (the Diagnostic Trail)
- Custom metadata declared by your site, such as a user ID or a release version, is attached. See [Custom metadata](/docs/widget/custom-metadata).
- A Recording of the last minute on the page is attached: the page's content as it changed and the Reviewer's interactions, without typed values. See [Recording](/docs/widget/recording).

All data is sent to the Faster Fixes API as a multipart form upload. The Recording follows in a second request, once the Feedback is created, so a slow or failed upload never holds up the Feedback.

## 2. API (server-side)

The API receives feedback, validates the request (API key, reviewer token, origin), stores the data, and uploads the screenshot to cloud storage. It then triggers background jobs:

- Create a GitHub issue (if GitHub integration is enabled)

## 3. Consumption layer

Feedback can be consumed two ways:

- **Dashboard**: A web interface where developers view, filter, assign, and manage feedback. Supports bulk actions, status management, and markdown export.
- **MCP Server**: An AI agent interface. The agent calls `list_feedbacks` to get structured feedback and `update_feedback_status` to mark items as resolved. The developer never leaves their terminal.

## Data flow

```
Reviewer clicks an element or drags over an area
        ↓
Widget captures context (screenshot, selector, component tree, browser info, console & network logs, Custom metadata, Recording)
        ↓
Feedback submitted to Faster Fixes API
        ↓
Recording uploaded to the created Feedback
        ↓
    ┌───────────┬──────────────┐
    ↓           ↓              ↓
Dashboard   MCP Server    GitHub Issue
    ↓           ↓              ↓
Developer   AI Agent     Issue Tracker
```
