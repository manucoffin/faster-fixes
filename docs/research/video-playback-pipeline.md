# Video playback and upload pipeline

> Research for issue #304 (part of the Video review map, #301). How a Video gets from the User's browser into object storage and back into a `<video>` element on the review page, without transcoding, on R2, S3, MinIO and local disk. Facts come from official docs, specs and the library source; anything not found there is marked UNVERIFIED.

Code read for this note: `apps/web/src/server/storage/*.ts`, `apps/web/src/app/api/upload/route.ts`, `apps/web/src/app/api/storage/[...path]/route.ts`, `apps/web/src/app/_components/upload-button.client.tsx`, `apps/web/src/proxy.ts`, `apps/web/src/app/api/v1/feedback/_services/create-feedback-screenshot.ts`, `docs/systems/asset-storage.md`, and the Next.js 16.3 docs under `apps/web/node_modules/next/dist/docs/`.

## Summary

1. Upload with better-upload `route({ multipart: true, partSize, maxFileSize, fileTypes: ["video/mp4", "video/quicktime", "video/webm"] })`: the server makes one CreateMultipartUpload call, the browser PUTs the parts and POSTs CompleteMultipartUpload against presigned URLs, progress is a 0..1 fraction per file, there is no resume (only per-request `retry`), and `AbortSignal` is the only cancel.
2. Pick a fixed part size between 5 MiB and 5 GiB (16 MiB is a safe default): R2 requires all parts but the last to be the same size, S3 and MinIO only require 5 MiB minimum, better-upload enforces neither. Bucket CORS must allow `GET, HEAD, PUT, POST, DELETE` from the app origin and expose `ETag` (the browser reads it for every part); MinIO community exposes it by default, R2 and S3 need a rule.
3. Local disk: `LocalStorage.uploadClient` implements only `buildBucketUrl` and `s3.sign`, so `multipart: true` throws on `client.s3.fetch`; the PUT route buffers the whole body with `req.arrayBuffer()` and the GET route uses `readFile`. Video on local disk needs a streamed single PUT with a documented max size (reverse proxy `client_max_body_size`, nginx default 1m) or a local multipart emulation, plus a streaming Range-aware GET.
4. Playback: keep the signed GET URL (1 hour is fine, cap is 7 days on all three providers) and `<video crossorigin="anonymous" preload="metadata">`. R2, S3 and MinIO all answer `Range` with 206 on the S3 API endpoint; do not sign the `Range` header. A streaming Next.js route is only needed for local disk, where the route must implement `Range` itself (`fs.createReadStream({ start, end })` wrapped with `Readable.toWeb`).
5. moov placement: a file with `moov` after `mdat` still plays over a Range-capable server (the browser fetches the tail first), at the cost of a start delay; detect it client-side by walking the top-level boxes (8-byte headers), warn the User, do not remux in the browser (ffmpeg.wasm is 31 MB and capped at 2 GB; mp4box.js has no documented faststart API).
6. Codec check before upload: `File.type` is extension-derived, so parse `ftyp` and the `stsd` sample entry fourcc (`avc1`/`avc3`, `hvc1`/`hev1`, `ap4h`), build a codecs string and ask `MediaCapabilities.decodingInfo()` (hard boolean, every engine since Safari 13) with `canPlayType()` as the fallback; refuse `hvc1`/`hev1`, ProRes and anything unknown with a clear message.
7. Frame capture: `drawImage(video)` is only origin-clean when the element has `crossorigin="anonymous"` set before `src` and the storage GET returns `Access-Control-Allow-Origin` for the review page origin; then `canvas.toBlob(cb, "image/jpeg", q)` and upload as a Screenshot through a route that accepts the blob (same path as widget screenshots: server-side `putStorageObject` plus `createAsset`).
8. Thumbnails: same mechanism, seek after `loadedmetadata`, wait for `seeked` (and `requestVideoFrameCallback` where available, Safari draws the wrong frame otherwise), draw at reduced size, `toBlob("image/jpeg")`, upload with the Video. No server-side ffmpeg needed.
9. Self-hosted: everything above works unchanged on S3 and MinIO (set `MINIO_API_CORS_ALLOW_ORIGIN` or keep its `*` default; MinIO ignores the `AbortIncompleteMultipartUpload` lifecycle rule but sweeps stale uploads after 24h). R2 aborts incomplete uploads after 7 days by default; S3 needs an explicit lifecycle rule.

### Local disk provider: what it can and cannot do

`LocalStorage.uploadClient` (`apps/web/src/server/storage/local.ts`) implements `buildBucketUrl` and `s3.sign` only, with the comment "Better Upload's non-multipart routes only use buildBucketUrl and s3.sign." The multipart handler calls `client.s3.fetch` for CreateMultipartUpload, which is `undefined` on the local client, so `multipart: true` cannot be used with the local provider as is. The signed local PUT URL also encodes `contentType` and `size`, and the route rejects a PUT whose `content-length` differs, so a per-part PUT (different sizes, `?partNumber=`) would need its own token shape.

The local PUT handler reads the whole body with `req.arrayBuffer()` and the GET handler with `readFile` (`route.ts`, `local.ts`), so a 2 GB video means 2 GB of process memory per request in both directions, and the GET route's `contentTypes` map only knows png/jpeg/webp (anything else is 404). Three facts bound a local single PUT:

- `/api/storage` is excluded from the proxy matcher (`apps/web/src/proxy.ts`: `"/((?!api|...).*)"` plus the two `/api/v1/...` prefixes), so Next.js does not clone the body into memory and the 10 MB `experimental.proxyClientMaxBodySize` truncation does not apply. The cloning only happens when the proxy runs for the request (`next/dist/server/next-server.js`, `requestData.body.cloneBodyStream()` inside the middleware branch; `next/dist/server/body-streams.js`). Docs: `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/proxyClientMaxBodySize.md`.
- A self-hosted instance normally sits behind a reverse proxy; nginx's `client_max_body_size` default is `1m` and the excess returns 413 ([nginx](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size)). The self-hosting guide must say to raise it (or set `0`) for video.
- On Vercel "The maximum payload size for the request body or the response body of a Vercel Function is 4.5 MB" ([Vercel limits](https://vercel.com/docs/functions/limitations)), which rules out the local provider for video on Vercel in both directions (it was never meant for Vercel; the guide says persistent disk).

Options for local disk, in increasing effort:

1. Single streamed PUT: keep the existing signed URL shape, replace `req.arrayBuffer()` with piping `req.body` to `fs.createWriteStream` and enforce the size from the token. Max size is whatever the reverse proxy allows; no progress difference for the client (XHR progress works on a single PUT). No resume, which is also true on the other providers.
2. Emulate multipart locally: implement `s3.fetch` for `?uploads` (return a fake `InitiateMultipartUploadResult`), accept `PUT ?partNumber=&uploadId=` into a temp directory, concatenate on `POST ?uploadId=`, delete on `DELETE`. This keeps one client code path and bounded request sizes. More code, and the `verifyLocalStorageAccess` token must learn part numbers.

Either way the GET side needs streaming with `Range` (section 2).

## 2. Playback

### Signed GET URL vs streaming route

The current pattern (`getSignedAssetUrl`, default `expiresIn = 3600`, `presignGetObject` under the hood with `X-Amz-Expires`) works for video on R2, S3 and MinIO: the `<video>` element fetches the presigned URL directly, the object store serves bytes and ranges, and the Next.js server only signs. The cap on expiry is 7 days on all three ("Timeout from 1 second to 7 days (604,800 seconds)" for R2, `X-Amz-Expires` max 604800 for S3, `ErrMaximumExpires` above 604800 in MinIO's `signature-v4-parser.go`): [R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), [IAM SigV4](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv-authentication-methods.html), [MinIO source](https://github.com/minio/minio/blob/master/cmd/signature-v4-parser.go). S3 checks expiry at request start: "if a client begins to download a large file immediately before the expiration time, the download continues even if the expiration time passes during the download" ([S3 presigned URLs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)). The browser issues a new Range request on every seek, so a review session longer than the URL lifetime breaks on the next seek: the review page should re-fetch a URL (or sign for the session's expected length, up to 7 days) rather than rely on 1 hour.

`Range` and signing: SigV4 only requires `host` and `x-amz-*` headers to be signed ([IAM SigV4](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv-authentication-methods.html)); do not sign `Range` (S3 then also requires `If-Range` to be signed, [S3 presigned URL FAQ](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)). `presignGetObject` does not sign it.

A streaming route through Next.js (server fetches from the bucket and pipes) adds a hop, costs server egress and CPU for every seek, and on Vercel hits the 4.5 MB response cap. It is not needed for R2/S3/MinIO. It is needed for local disk, where the route is the storage.

`response-content-type` / `response-content-disposition` on the presigned GET: supported on S3 ([GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html)), UNVERIFIED on R2 (not in the R2 GetObject header list) and MinIO. Store the right `Content-Type` at upload instead: better-upload signs `content-type` into the part/PUT request, R2 locks a presigned PUT to the signed Content-Type (403 otherwise), and the stored type is served back on GET (R2: implied by S3 compatibility and the Workers `httpMetadata` description, UNVERIFIED by an explicit S3-API sentence).

### Range request support

Browsers seek with HTTP Range: the HTML media fetch algorithm adds a `Range` header and accepts 200 or 206 ([HTML spec, media resource fetch](https://html.spec.whatwg.org/multipage/media.html#concept-media-load-resource)); Apple: "HTTP servers hosting media files for iOS must support byte-range requests, which iOS uses to perform random access in media playback" ([Safari web content guide](https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/CreatingVideoforSafarioniPhone/CreatingVideoforSafarioniPhone.html)); MDN: "It must return 206 Partial Content to all range requests, otherwise browsers can't determine if the server supports range requests" and "must also return 206 for `Range: bytes=0-`" ([MDN, configuring servers](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Configuring_servers_for_Ogg_media)). WebKit bug 221622 reports Safari marking videos as broken without Range and Content-Length ([bug](https://bugs.webkit.org/show_bug.cgi?id=221622)).

The local GET route also sends `Content-Security-Policy: default-src 'none'` and `X-Content-Type-Options: nosniff`; both are fine for a `<video src>` as long as `Content-Type` is `video/mp4`. Add `video/mp4`, `video/quicktime`, `video/webm` to the `contentTypes` map (or store the type with the object) and keep `Cache-Control: private, no-store`, since the token is in the URL. Multiple-range requests can be answered with the first range or 416; browsers only send single ranges for media (UNVERIFIED as a spec statement; the HTML fetch algorithm adds a single `bytes=N-` header).

### moov atom placement (faststart)

Apple: "If the movie atom is stored at the beginning of the file, the application can use the meta-data to understand the movie's content as it is acquired over the network. This can allow an application to play a movie as it downloads." ([QTFF 2001, Basic Atom Types](https://developer.apple.com/standards/qtff-2001.pdf)); `mdat` "can be understood only by using the metadata stored in the movie atom" ([movie data atom](https://developer.apple.com/documentation/quicktime-file-format/movie_data_atom)); `ftyp` must be first ([file type atom](https://developer.apple.com/documentation/quicktime-file-format/file_type_compatibility_atom)). ffmpeg: moov "is usually written at the end of the file, but it can be moved to the start for better playback" with `-movflags faststart`, "a second pass moving the index (moov atom) to the beginning of the file" ([ffmpeg formats](https://ffmpeg.org/ffmpeg-formats.html)). Phone recordings and most editors already write faststart; screen recorders and some cameras do not.

Browser behaviour with `moov` at the end over a Range-capable server: the browser reads the head, finds `mdat`, and fetches the tail to get `moov` before it can show a frame (MDN documents the same end-of-file byte-range probe for duration). Result is a start delay, not a failure. Without Range support the browser must download the whole file first. No official source quantifies the delay: UNVERIFIED beyond the mechanism.

Detect client-side before upload: read the first 8 bytes at offset 0 with `file.slice(offset, offset + 16).arrayBuffer()`, parse `size` (uint32) and `type` (fourcc); `size === 1` means a 64-bit `largesize` follows the type, `size === 0` means "to end of file" ([atoms](https://developer.apple.com/documentation/quicktime-file-format/atoms)); skip to `offset + size` and repeat. If `moov` appears before `mdat`, the file is faststart. Cost: a few hundred bytes read, no full-file scan. Suggested UX: accept the file but show "This video will take longer to start playing. Export it with 'fast start' (web optimized) for a better review experience." Refusing is not warranted since playback works.

Fix client-side: a remux (move `moov` before `mdat` and add the moov size to every `stco`/`co64` offset, [chunk offset atom](https://developer.apple.com/documentation/quicktime-file-format/chunk_offset_atom)). Candidates: ffmpeg.wasm (`-c copy -movflags +faststart`; core is "~31 MB", "2 GB, which is a hard limit in WebAssembly", LGPL/GPL core, [ffmpeg.wasm FAQ](https://ffmpegwasm.netlify.app/docs/faq)), mp4box.js (BSD-3, can write boxes, no documented faststart API: UNVERIFIED), or a hand-written box rewriter (~200 lines, only `stco`/`co64` need patching, UNVERIFIED as an exhaustive list: `moof`-based fragmented files and edit lists differ). Recommendation: warn only, do not remux in v1; a server-side `ffmpeg -movflags +faststart` pass is transcoding-free but needs ffmpeg on the self-hosted box, which the map rules out ("without transcoding", no new services).

## 3. Codec detection in the browser before upload

Map fact: only MP4 H.264/AAC plays everywhere; HEVC is partial in Chrome, ProRes is Safari-only. The checks:

| `File.type`                                                                                                             | MIME guessed from the extension: "browsers won't actually read the bytestream of a file to determine its media type" | `.mov` gives `video/quicktime` regardless of codec; `.mp4` can hold HEVC. All three need a codecs string, which only the container can give. Where it is: `moov > trak > mdia > minf > stbl > stsd`, each sample description entry starting with a 32-bit size and the 32-bit "Data format" fourcc ([sample description atom](https://developer.apple.com/documentation/quicktime-file-format/sample_description_atom), [movie atoms](https://developer.apple.com/documentation/quicktime-file-format/movie_atoms)). Fourccs: `avc1`/`avc3` H.264, `hvc1`/`hev1` HEVC, `mp4v` MPEG-4 Part 2, `ap4h`/`apch`/... ProRes (Apple lists `avc1` and `mp4v` in the [video sample description](https://developer.apple.com/documentation/quicktime-file-format/video_sample_description) table and `hvc1` in its HEVC-with-alpha profile; the literal ProRes fourccs are UNVERIFIED from Apple docs, they come from the Core Media constant names). Audio: `mp4a` with AAC-LC = `mp4a.40.2` ([MDN codecs parameter](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/codecs_parameter)). The full `avc1.PPCCLL` string comes from the `avcC` box inside the `avc1` entry (profile, constraints, level bytes); for HEVC from `hvcC`.

Reading `stsd` requires the `moov` box, which may be at the end of the file (section 2): the parser must walk top-level boxes, then `file.slice(moovOffset, moovOffset + moovSize)` (usually under a few MB) and walk into it. This is the same walk as the faststart check, so one pass gives both answers. WebM (`video/webm`, EBML, codec id in `CodecID`) is a different parser; given "only MP4 H.264/AAC plays everywhere", accept `video/mp4` and `video/quicktime` containers in v1 and parse ISO BMFF only (recommendation, not a sourced fact).

Decision rule proposed: refuse when the video fourcc is not `avc1`/`avc3`, or when `decodingInfo().supported` is false in the uploading browser (fallback `canPlayType(...) === ""`), with the message naming the codec ("This video uses HEVC (H.265), which does not play in every browser. Export it as H.264 MP4."). The uploader's browser passing does not prove a Reviewer's will, hence the fourcc allowlist rather than the capability check alone. Audio codecs other than AAC (`mp4a.40.2`) or none: warn, do not refuse (UNVERIFIED which audio codecs fail where; not researched).

## 4. Frame capture to a Screenshot

Tainting rule: "As soon as you draw into a canvas any data that was loaded from another origin without CORS approval, the canvas becomes tainted", and then `getImageData()`, `toBlob()`, `toDataURL()`, `captureStream()` throw `SecurityError` ([MDN CORS enabled image](https://developer.mozilla.org/en-US/docs/Web/HTML/How_to/CORS_enabled_image)). Spec: a video is not origin-clean when "image's media data is CORS-cross-origin", and `drawImage` then clears the canvas's origin-clean flag ([HTML canvas spec](https://html.spec.whatwg.org/multipage/canvas.html#drawing-images)).

Conditions for a clean canvas from a presigned storage URL (different origin than the review page):

1. `<video crossorigin="anonymous">`: the media fetch becomes a CORS request with no credentials ([MDN crossorigin](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/crossorigin), [HTML CORS settings attributes](https://html.spec.whatwg.org/multipage/urls-and-fetching.html#cors-settings-attributes)). Without the attribute the fetch is `no-cors` and the canvas is always tainted. Set the attribute before `src` (MDN shows this order; UNVERIFIED as a stated rule, but in React both are props on the same element so the order question does not arise).
2. The storage GET must return `Access-Control-Allow-Origin` for the review page origin (or `*`), which is the bucket CORS rule from section 1 (`AllowedMethods: GET`, `AllowedOrigins: <app origin>`). R2 only adds CORS headers when the request has an `Origin` header ([R2 CORS](https://developers.cloudflare.com/r2/buckets/cors/)), which `crossorigin` guarantees. If the server does not answer with CORS headers, the CORS-mode fetch is a network error and the element fires `error` with `MEDIA_ERR_SRC_NOT_SUPPORTED` rather than playing tainted (Fetch spec step "return a network error" on a failed CORS check: UNVERIFIED verbatim; the media spec failure path is at [HTML media load algorithm](https://html.spec.whatwg.org/multipage/media.html#concept-media-load-algorithm)). So the playback itself proves the CORS setup: if the video plays with `crossorigin="anonymous"`, the canvas will be clean.
3. Local disk: the review page and `/api/storage` share an origin, so the fetch is same-origin and never taints; the route's `Access-Control-Allow-Origin: *` is harmless. Keep `crossorigin="anonymous"` anyway so one code path serves every provider (a same-origin CORS request is allowed).
4. The signed URL changes per request (new `X-Amz-Signature`), which does not matter for CORS: the check is on the origin of the URL, not the full URL. A CDN or public bucket URL (`NEXT_PUBLIC_STORAGE_BASE_URL`) would need the same CORS rule; a Reviewer must not get a download link, so the review page should use signed URLs only (map: download of the original is out of scope).

Capture: `ctx.drawImage(video, 0, 0, video.videoWidth, video.videoHeight)` draws "the frame at the current playback position"; it draws nothing when `readyState` is `HAVE_NOTHING` or `HAVE_METADATA` ([canvas spec](https://html.spec.whatwg.org/multipage/canvas.html#drawing-images)); MDN: works "when its readyState is greater than 1 (i.e., seek event fired after setting the currentTime property)" ([drawImage](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage)). `videoWidth`/`videoHeight` are the intrinsic size in CSS pixels, 0 before metadata ([videoWidth](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/videoWidth)). Export with `canvas.toBlob(cb, "image/jpeg", quality)`; default type is `image/png` "that type is also used if the given type isn't supported"; `cb` receives `null` if the image cannot be created ([toBlob](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/toBlob)). For a 1080p frame JPEG at 0.85 is a few hundred KB, PNG several MB (UNVERIFIED size estimate; measure).

Upload path: the widget already posts screenshots as a `File` in `multipart/form-data` to `/api/v1/feedback`, 5 MB cap, PNG/JPEG/WebP, stored by `createFeedbackScreenshot` with `putStorageObject` and `createAsset` (`apps/web/src/app/api/v1/feedback/route.ts` and `_services/create-feedback-screenshot.ts`). The review page can reuse that server-side pattern on its own route (Share link token instead of widget key, rate-limited like anonymous writes). Note `/api/v1/feedback` is under the proxy matcher, so bodies there are subject to the 10 MB proxy clone limit; a new route under another `/api/...` prefix is not. Alternatively presign a `screenshot` better-upload route for a direct PUT, which keeps bytes off the server but needs the two-step create.

## 5. Thumbnail generation client-side

Same mechanism, run once in the uploader's browser from the local `File` (object URL, same origin, no CORS at all) before or during the upload:

1. `video.preload = "metadata"; video.src = URL.createObjectURL(file)`; wait for `loadedmetadata` (duration and dimensions known, [loadedmetadata](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/loadedmetadata_event)).
2. Set `currentTime` (seeking returns early if `readyState` is `HAVE_NOTHING`, [seek algorithm](https://html.spec.whatwg.org/multipage/media.html#dom-media-seek)); wait for `seeked`, which fires once the position is decodable ([seeked](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/seeked_event)). Do not use `timeupdate`, it is rate-limited (4 to 66 Hz) and not tied to a decoded frame ([timeupdate](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/timeupdate_event)).
3. Safari: WebKit bugs 236755 and 194986 report `seeked` firing before the frame is displayed on the native MP4 path, so `drawImage` captures frame 0 ([236755](https://bugs.webkit.org/show_bug.cgi?id=236755), [194986](https://bugs.webkit.org/show_bug.cgi?id=194986)). Mitigation with an official basis: wait for `requestVideoFrameCallback` (fires "when a new video frame is sent to the compositor"; Chrome 83, Firefox 132, Safari 15.4, [MDN](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)) after the seek, and check `readyState >= HAVE_CURRENT_DATA`. The common "wait for `canplay`" workaround is UNVERIFIED.
4. Draw at reduced size (`drawImage(video, 0, 0, w, h)` scales), `toBlob(cb, "image/jpeg", 0.8)`, upload as a second object (`videos/<id>/thumbnail.jpg`) alongside the Video, or post it with the create mutation.

This answers the "Thumbnails and poster image in the Videos list" fog item without any server-side media tooling: poster = `<video poster={thumbnailUrl}>` with a signed URL, and the same code produces the frame for a Screenshot on the review page. The uploader's browser must be able to decode the file, which section 3 already requires. Pick the frame at a fixed offset (for example 1 s or 10 percent of duration) to avoid black lead-in frames (UNVERIFIED heuristic, not from a source).

## Open points for the spec

- Local disk: choose between a streamed single PUT (simple, size bounded by the reverse proxy) and a multipart emulation (one client path). Both need the GET route to stream with Range and to serve video content types.
- Signed URL lifetime on the review page: refresh strategy for sessions longer than the URL (seek after expiry fails), or sign for longer.
- The server never sees upload completion with better-upload; the Video "uploaded" state comes from the client mutation, and orphan objects rely on lifecycle rules (R2 default, S3 rule to document, MinIO sweeper) plus our own cleanup for objects that completed but were never registered.
- Self-hosting guide additions: bucket CORS rule with `ETag` exposed, reverse proxy body size for local disk, S3 lifecycle rule.
